KV cache lớn dần theo token

Mỗi token được xử lý sẽ để lại Key và Value ở các layer để model dùng lại. Thử đổi số phiên, kiểu attention và độ chính xác cache để nhìn vì sao prompt dài có thể chiếm nhiều VRAM.

Đừng nhầm với weights: Weights là bộ nhớ model đã nạp; KV cache là trạng thái riêng cho những token trong từng phiên đang chạy. Cùng một model có thể dùng chung weights, còn mỗi phiên giữ cache K/V của nó.

Profile minh họa: 32 layers, 32 query heads, head dimension 128; chỉ số KV heads thay đổi theo MHA/GQA/MQA. Mỗi phiên dùng cùng độ dài cache để dễ so sánh.

Đang tính…

M_KV ≈ 2 × layers × tokens × KV heads × head dimension × bytes × số phiên

“2” là Key và Value. T ở đây là số token đã xử lý trong mỗi phiên; cache bytes được nhân với số phiên hoạt động.

Cache hiện bằng 0 token. Chọn cấu hình rồi nạp từng khúc hoặc chạy tới hết context.

Context dài → cache lớn

Thêm token nghĩa là mỗi layer cần giữ thêm K/V để dùng cho bước sinh tiếp theo. Cache tăng theo tổng số token đang sống.

GQA chia sẻ KV heads

GQA dùng ít KV heads hơn số query heads; MQA dùng một KV head. Điều đó có thể giảm cache, nhưng đây là lựa chọn kiến trúc của model, không phải nút miễn phí đổi cho mọi model.

Precision của KV là riêng

INT8/INT4 cache có thể giảm dung lượng nếu model, runtime và backend hỗ trợ. Quantize weights không tự động làm KV cache nhỏ đi.

Điểm nhớ: Ước tính KV tăng tuyến tính theo token, số phiên, KV heads và bytes mỗi giá trị. VRAM tổng còn có weights, workspace, activations và phân mảnh allocator.

Giả định số học để cô lập ý tưởng: L=32, Hq=32, D=128; MHA dùng Hkv=32, GQA=8, MQA=1; cache FP16 dùng 2 bytes mỗi phần tử. Mặc định weights Q4 ≈4,5 GiB và workspace ≈1 GiB chỉ để minh họa ngân sách. INT8/INT4 dùng bytes danh nghĩa, chưa cộng scale/metadata và layout overhead. Kiến trúc, cache dtype và hỗ trợ backend thay đổi theo model/runtime.
