BẢN ĐỒ KHÁI NIỆM

Bảy pattern,
bảy vai trò khác nhau.

Mỗi mục có định nghĩa, cơ chế, khi nên dùng, trade-off và một điểm dễ nhầm.

01Zero-shot / One-shot promptingĐưa task trực tiếp vào prompt⌄

TL;DR: Zero-shot không đưa ví dụ; one-shot đưa một ví dụ. Cả hai thường chỉ cần một lần gọi LLM.

Cơ chế hoạt động

  • Zero-shot: chỉ có instruction + task.
  • One-shot: thêm một mẫu input/output làm gợi ý.
  • Không gọi tool và không tạo vòng lặp chỉ vì dùng prompt.

Khi nào dùng / tránh

Dùng cho tác vụ rõ, ngắn, có thể mô tả tốt bằng instruction. Nếu format hoặc style khó diễn đạt, thử few-shot; nếu cần dữ liệu ngoài, thêm tool.

Ví dụ thực tế

“Phân loại ticket này thành Bug, Question hoặc Feature” — không cần ví dụ mẫu (zero-shot).

Cost & latency

Thường 1 LLM call; latency và chi phí thấp nhất trong các pattern ở đây.

Đừng nhầm: zero-shot và one-shot chỉ khác số ví dụ trong context; one-shot không phải fine-tune.
02Few-shot / Multiple-shot promptingNhiều ví dụ nằm trong context⌄

TL;DR: Cho LLM xem vài ví dụ input/output trước task mới để bắt chước pattern ngay trong context window.

Cơ chế hoạt động

  • Prompt gồm instruction, ví dụ mẫu và query mới.
  • Model suy ra style, nhãn hoặc cấu trúc từ examples.
  • Ví dụ được gửi cùng request; trọng số model không đổi.

Khi nào dùng / tránh

Dùng khi cần format nhất quán hoặc instruction khó diễn đạt. Tránh nhồi ví dụ dài, trùng lặp hay mâu thuẫn vì tốn context và có thể gây nhiễu.

Ví dụ thực tế

Đưa ba cặp câu tiếng Việt → nhãn cảm xúc để model gán nhãn cho câu mới theo cùng quy tắc.

Cost & latency

Thường vẫn 1 call; prompt dài hơn nên tốn token, context và có thể tăng latency.

Few-shot ≠ Fine-tune: few-shot thêm ví dụ vào request; fine-tuning cập nhật/điều chỉnh model weights qua quy trình huấn luyện.
03Planning / DecompositionChia task thành các bước có thứ tự⌄

TL;DR: Lập kế hoạch hoặc phân rã bài toán thành các bước; planning có thể chạy một hoặc nhiều LLM calls nhưng tự nó không phải loop dùng tool.

Cơ chế hoạt động

  • Phân tích mục tiêu, xác định subtask và thứ tự phụ thuộc.
  • Thực hiện tuần tự hoặc tổng hợp các bước.
  • Chain-of-thought, Plan-and-Solve và decomposition là kỹ thuật liên quan nhưng không đồng nhất hoàn toàn.

Khi nào dùng / tránh

Dùng cho bài toán nhiều bước logic có cấu trúc. Không cần planning cầu kỳ cho câu hỏi đơn giản; dùng agent nếu cần lặp theo observation mới.

Ví dụ thực tế

Giải bài toán: đọc đề → đặt biến → lập phương trình → kiểm tra kết quả.

Cost & latency

Từ 1 tới nhiều calls tùy thiết kế; thêm bước trung gian có thể tăng độ trễ.

Planning ≠ Agent: kế hoạch mô tả các bước; agent có loop chọn hành động dựa trên observation và có thể điều chỉnh kế hoạch.
04Tool Use / Function CallingLLM đề xuất hàm · runtime thực thi⌄

TL;DR: LLM phát ra yêu cầu gọi hàm có cấu trúc; ứng dụng/runtime mới thực thi tool và gửi kết quả lại cho LLM.

Cơ chế hoạt động

  • Model chọn tên tool và arguments theo schema.
  • Runtime kiểm tra quyền/đầu vào rồi thực thi function.
  • Tool result trở lại model để tạo câu trả lời.

Khi nào dùng / tránh

Dùng khi cần dữ liệu hoặc hành động ngoài model như tra cứu, tính toán hay đọc database. Chỉ cấp quyền tối thiểu; xác nhận người dùng với hành động nhạy cảm.

Ví dụ thực tế

Gọi weather(city="Hanoi") rồi dùng kết quả giả lập để trả lời thời tiết. App, không phải LLM, thực thi function.

Cost & latency

Thường 2 LLM calls cho một vòng tool: request → tool → response; cộng thêm thời gian chạy tool.

Tool Use ≠ Agent: một lần gọi tool có thể kết thúc ngay; agent thường lặp nhiều vòng dựa trên observation.
05Agent · ReAct loopThought → Action → Observation → lặp⌄

TL;DR: Agent là pattern điều phối lặp: chọn action, quan sát kết quả, rồi quyết định tiếp cho đến khi đạt goal hoặc dừng.

Cơ chế hoạt động

  • ReAct thường mô tả chu trình reasoning, action và observation.
  • Loop controller gửi kết quả mới về model qua nhiều bước.
  • Production cần giới hạn vòng lặp, quyền tool, timeout và tiêu chí dừng.

Khi nào dùng / tránh

Dùng cho nhiệm vụ mở, nhiều bước và phụ thuộc kết quả mới. Tránh agent nếu workflow cố định và một lời gọi tool là đủ.

Ví dụ thực tế

Tra mã đơn → kiểm tra trạng thái vận chuyển → tổng hợp tình trạng giao hàng (dữ liệu demo).

Cost & latency

Số calls động theo số vòng; thường tốn latency/token hơn và cần giám sát chặt.

Tool Use một lần ≠ Agent loop: agent có thể dùng tools, nhưng điểm cốt lõi là vòng lặp có observation và quyết định tiếp.

“Thought” trong sơ đồ là nhãn minh họa cho bước điều phối; không hàm ý ứng dụng nên phơi bày chain-of-thought nội bộ của model.

06SkillGói capability có thể tái sử dụng⌄

TL;DR: Skill đóng gói hướng dẫn, tools được phép và ví dụ/workflow thành một capability có thể gọi lại.

Cơ chế hoạt động

  • Instructions mô tả mục tiêu, quy trình và ràng buộc.
  • Allowed tools nêu các hành động capability có quyền dùng.
  • Examples giúp chuẩn hóa cách xử lý.

Khi nào dùng / tránh

Dùng cho năng lực lặp lại ở nhiều task/agent. Không cần đóng gói nếu chỉ có một function nhỏ hoặc workflow rất đơn giản.

Ví dụ thực tế

Skill “summarize_article” có hướng dẫn tóm tắt, tool đọc bài viết và ví dụ đầu ra ngắn.

Cost & latency

Không có số calls cố định; phụ thuộc flow bên trong. Có chi phí duy trì, test và versioning capability.

Skill ≠ Tool: tool là một function/action nguyên thủy; skill là gói capability có thể dùng một hoặc nhiều tools và bước xử lý.
07HarnessRuntime bao quanh và điều phối LLM⌄

TL;DR: Harness là lớp runtime quản lý context, tool registry, memory, loop controller, guardrails và việc gọi model.

Cơ chế hoạt động

  • Build context, nối system prompt, schema và history.
  • Điều phối model/tool loop, lưu trạng thái và kết quả.
  • Áp dụng policy, logging, retry, timeout và kiểm tra an toàn.

Khi nào dùng / tránh

Cần harness khi triển khai production, cần khả năng quan sát và kiểm soát. Prototype nhỏ có thể dùng runtime tối giản nhưng vẫn cần xử lý quyền an toàn.

Ví dụ thực tế

Runtime kiểm tra tool call xóa dữ liệu, chặn hành động không được phép rồi yêu cầu bước xác nhận.

Cost & latency

Thêm overhead điều phối/logging/guardrails; độ trễ tổng phụ thuộc model calls và tools.

Harness ≠ Agent: agent là pattern hành vi; harness là runtime có thể chạy agent, tool call đơn lẻ hoặc workflow khác.
