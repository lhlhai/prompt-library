Path 1: Lightning-Fast Log Search

Lesson 1.1 Term vs Match: When to Use Which?
Use case: You have a transaction ID TX12345. Use term for exact match. You have a log message "User login failed". Use match for full-text search.
JSON DSL
{
  "query": {
    "bool": {
      "must": [
        { "term": { "transaction_id.keyword": "TX12345" } },
        { "match": { "message": "failed" } }
      ]
    }
  }
}
Pro-tip: Always use .keyword for text fields if you want exact matching (case-sensitive). Regular text fields are analyzed and tokenized into individual words.
Challenge: Write a query to find logs with request_id equal to "REQ-999" and message containing the word "timeout".
🎯 Practice Exercise 1: Find all logs where status_code is exactly 500 (use term) AND message contains either "database" or "connection" (use match with OR).
🎯 Practice Exercise 2: Create a query that matches logs with user_type exactly equal to "admin" but the message should contain "failed" or "error" (case-insensitive).
💡 Quick Exercise: Try modifying the query above to search for multiple keywords in the message field using the OR operator.
Lesson 1.2 Wildcard & Fuzzy: Finding When You're Not Sure
Use case: Find logs from services starting with auth-* or find misspelled keywords (e.g., conection instead of connection).
JSON DSL
{
  "query": {
    "bool": {
      "should": [
        { "wildcard": { "service.keyword": "auth-*" } },
        { "fuzzy": { "message": { "value": "conection", "fuzziness": 1 } } }
      ]
    }
  }
}
Pro-tip: Wildcards can be slow on large datasets. Use them sparingly and prefer prefix wildcards (auth-*) over suffix wildcards (*-service).
Challenge: Find all logs from services containing "payment" (using wildcard) with error messages similar to "database".
🎯 Practice Exercise 1: Find logs from services matching pattern *-api with fuzzy search for "databse" (misspelling of database).
🎯 Practice Exercise 2: Create a query that finds error codes starting with ERR_ OR ERROR_, and also search for similar terms to "timeout" with fuzziness of 2.
💡 Quick Exercise: Experiment with different fuzziness values (0, 1, 2) and observe how results change.
Lesson 1.3 Range & Time: Filtering by Time
Use case: Find logs in the last 24 hours or find requests with extremely high response times (latency).
JSON DSL
{
  "query": {
    "range": {
      "@timestamp": {
        "gte": "now-24h",
        "lte": "now"
      }
    }
  }
}
Pro-tip: Use operators gte (>=), gt (>), lte (<=), lt (<). For time, shortcuts like now-1d, now-1h are extremely useful.
Challenge: Find logs with response_time greater than 5000ms between 2 days ago and 1 day ago.
🎯 Practice Exercise 1: Find all ERROR logs from the last 6 hours with response_time between 1000ms and 5000ms.
🎯 Practice Exercise 2: Create a query to find logs from the current week (Monday to now) with request_size greater than 1MB.
🎯 Practice Exercise 3: Find logs where timestamp is in a specific date range (e.g., 2024-01-01 to 2024-01-31) and latency is less than 100ms.
💡 Quick Exercise: Create a query that finds logs from the beginning of the current month until now.
Lesson 1.4 Bool Logic: Combining Conditions
Use case: Combine multiple conditions: Must be an error, Must be within 1 hour, and Must NOT be from service test-bot.
JSON DSL
{
  "query": {
    "bool": {
      "must": [ { "match": { "level": "ERROR" } } ],
      "filter": [ { "range": { "@timestamp": { "gte": "now-1h" } } } ],
      "must_not": [ { "term": { "service.keyword": "test-bot" } } ]
    }
  }
}
Pro-tip: Always prefer filter over must for true/false conditions (like time, status codes) because filter is faster and cached.
Challenge: Build a query that finds ERROR logs from the last 2 hours, excluding service "monitoring", but only for user_id starting with "VIP".
🎯 Practice Exercise 1: Find logs where (status_code is 4xx OR 5xx) AND (response_time > 2000ms) AND (NOT from service "cache").
🎯 Practice Exercise 2: Create a query with nested bool logic: Find logs where (service is "payment" OR "checkout") AND (level is "ERROR" OR "WARN") AND (timestamp is last 24h) AND (NOT from test environment).
🎯 Practice Exercise 3: Build a complex query with MUST, SHOULD, and MUST_NOT clauses to find high-priority issues.
Lesson 1.5 Exists & Missing: Checking Field Presence
Use case: Find all logs that have a user_id field (regardless of value) or find logs missing critical fields like error_code.
JSON DSL
{
  "query": {
    "bool": {
      "must": [
        { "exists": { "field": "user_id" } }
      ],
      "must_not": [
        { "exists": { "field": "error_code" } }
      ]
    }
  }
}
Pro-tip: The exists query checks if a field has any non-null value. Empty strings "" are considered existing values!
Challenge: Find all logs that have both customer_id AND order_id fields, but are missing refund_amount.
🎯 Practice Exercise 1: Find logs with trace_id present AND span_id present, but error_message is missing.
🎯 Practice Exercise 2: Create a query to find incomplete records: has user_id but missing session_id or request_id.
💡 Quick Exercise: Count how many logs in your index are missing the trace_id field (hint: use aggregation with exists filter).
Lesson 1.6 Prefix & Suffix: Pattern Matching
Use case: Find all error codes starting with ERR_ or URLs ending with .json. More efficient than wildcards for simple patterns.
JSON DSL
{
  "query": {
    "bool": {
      "must": [
        { "prefix": { "error_code.keyword": "ERR_" } },
        { "suffix": { "url.keyword": ".json" } }
      ]
    }
  }
}
Pro-tip: Prefix queries are faster than wildcard queries because they can use term dictionaries efficiently. Use them when possible!
Challenge: Find all logs where request_path starts with /api/v2/ and content_type ends with /json.
🎯 Practice Exercise 1: Find all service names starting with "svc-" and ending with "-prod".
🎯 Practice Exercise 2: Create a query to find logs where error_code starts with "DB_" OR "API_" and message ends with "timeout".
Lesson 1.7 Regex Search: Advanced Pattern Matching
Use case: Find logs with complex patterns like phone numbers, email addresses, or IP addresses using regular expressions.
JSON DSL
{
  "query": {
    "bool": {
      "must": [
        { "regexp": { "email.keyword": ".*@example\\.com" } },
        { "regexp": { "ip_address.keyword": "192\\.168\\..*" } }
      ]
    }
  }
}
Pro-tip: Regex queries are powerful but can be slow. Use them carefully and consider using prefix/wildcard queries when possible for better performance.
Challenge: Write a regex query to find all logs with phone numbers in format XXX-XXX-XXXX.
🎯 Practice Exercise 1: Find logs with IPv4 addresses in the 10.0.0.0/8 range.
🎯 Practice Exercise 2: Create a regex query to find error messages with specific error codes like ERR_001, ERR_002, etc.
Lesson 1.8 Complex Filtering: Real-World Scenarios
Use case: Combine multiple search techniques to solve real-world problems like finding security issues, performance problems, or data quality issues.
JSON DSL - Security Issue Detection
{
  "query": {
    "bool": {
      "must": [
        { "match": { "message": "unauthorized OR forbidden" } }
      ],
      "filter": [
        { "range": { "@timestamp": { "gte": "now-1h" } } },
        { "range": { "attempt_count": { "gte": 5 } } }
      ],
      "must_not": [
        { "term": { "source_ip.keyword": "127.0.0.1" } }
      ]
    }
  }
}
Pro-tip: Combine multiple techniques to create powerful queries that solve real business problems. Always test your queries on sample data first.
Challenge: Create a comprehensive query to detect potential DDoS attacks: Multiple failed requests from same IP in short time window, high request rate, and specific error patterns.
🎯 Practice Exercise 1: Build a query to find performance degradation: Response times > 2x normal average, happening in last hour, for specific services.

Path 2: Log Data Analysis

Lesson 2.1 Basic Aggregations: Quick Statistics
Use case: Calculate average response time or find the slowest request in the system.
JSON DSL
{
  "size": 0,
  "aggs": {
    "avg_latency": { "avg": { "field": "latency" } },
    "max_latency": { "max": { "field": "latency" } },
    "min_latency": { "min": { "field": "latency" } },
    "sum_bytes": { "sum": { "field": "bytes_sent" } }
  }
}
Pro-tip: Always set "size": 0 when you only need aggregations to avoid returning unnecessary documents and improve performance.
Challenge: Write a query to calculate the sum of bytes_sent for all requests with status 200.
🎯 Practice Exercise 1: Calculate multiple statistics: average, min, max, and sum of response_time for all logs.
🎯 Practice Exercise 2: Find the count of total requests, successful requests (200), and failed requests (4xx, 5xx).
💡 Quick Exercise: Add a count aggregation to see how many documents were analyzed.
Lesson 2.2 Grouping: Terms & Date Histograms
Use case: Count errors by service or create a time-series chart of errors per minute/hour.
JSON DSL
{
  "size": 0,
  "aggs": {
    "errors_by_service": {
      "terms": {
        "field": "service.keyword",
        "size": 10
      }
    },
    "errors_over_time": {
      "date_histogram": {
        "field": "@timestamp",
        "fixed_interval": "1h"
      }
    }
  }
}
Pro-tip: Combine terms aggregation inside date_histogram to see top errors in each time bucket. Use calendar_interval for human-readable intervals like "1d", "1M".
Challenge: Create a query that shows error count grouped by status_code for the last 24 hours.
🎯 Practice Exercise 1: Group logs by environment (prod, staging, dev) and count requests for each.
🎯 Practice Exercise 2: Create a date histogram with 15-minute intervals showing request count over time.
🎯 Practice Exercise 3: Build a query grouping by both service AND status_code to see which services have most errors.
💡 Quick Exercise: Modify the date_histogram to use 15-minute intervals instead of 1 hour.
Lesson 2.3 Advanced Statistics: Percentiles & Cardinality
Use case: Find the P95 latency (95% of users have response time below this value). This is more meaningful than average! Also count unique customers affected by errors.
JSON DSL
{
  "size": 0,
  "aggs": {
    "latency_percentiles": {
      "percentiles": {
        "field": "latency",
        "percents": [50, 75, 95, 99]
      }
    },
    "unique_customers": {
      "cardinality": {
        "field": "customer_id.keyword"
      }
    }
  }
}
Pro-tip: P95/P99 are crucial SLA metrics. Cardinality uses HyperLogLog++ for approximate counting - it's memory efficient but may have ~1% error on very large datasets.
Challenge: Calculate the number of unique customer_id values that encountered errors in the last 24 hours.
🎯 Practice Exercise 1: Find P50, P90, P95, P99, P99.9 latencies to understand full distribution.
🎯 Practice Exercise 2: Count unique users, unique sessions, and unique request IDs affected by errors.
🎯 Practice Exercise 3: Calculate percentiles for different status codes separately (200 vs 5xx).
💡 Quick Exercise: Add a percentile_ranks aggregation to find what percentile a specific latency value (e.g., 500ms) falls into.
Lesson 2.4 Nested Aggregations: Multi-Level Analysis
Use case: First group by service, then within each service, show errors by status code, and calculate average latency for each combination.
JSON DSL
{
  "size": 0,
  "aggs": {
    "by_service": {
      "terms": { "field": "service.keyword" },
      "aggs": {
        "by_status": {
          "terms": { "field": "status_code" },
          "aggs": {
            "avg_latency": { "avg": { "field": "latency" } }
          }
        }
      }
    }
  }
}
Pro-tip: Nested aggregations can go multiple levels deep, but be careful about performance. Each level multiplies the number of buckets!
Challenge: Create a 3-level aggregation: Group by date (daily), then by service, then calculate error rate (count of ERROR / total count).
🎯 Practice Exercise 1: Build a 3-level aggregation: date → service → status_code with count and average latency.
🎯 Practice Exercise 2: Create nested aggregations to find: top 5 services → top 3 error codes per service → count of occurrences.
🎯 Practice Exercise 3: Build a query with 4 levels: environment → service → endpoint → status_code with metrics.
Lesson 2.5 Filters in Aggregations: Targeted Analysis
Use case: Compare metrics between different user segments (VIP vs regular), or analyze error rates before/after a deployment.
JSON DSL
{
  "size": 0,
  "aggs": {
    "vip_users": {
      "filter": { "prefix": { "user_id.keyword": "VIP_" } },
      "aggs": {
        "avg_latency": { "avg": { "field": "latency" } }
      }
    },
    "regular_users": {
      "filter": { "wildcard": { "user_id.keyword": "USER_*" } },
      "aggs": {
        "avg_latency": { "avg": { "field": "latency" } }
      }
    }
  }
}
Pro-tip: Use filters (plural) aggregation when you need multiple named filters in one go. It's more efficient than running separate queries.
Challenge: Compare error counts between production environment (env: "prod") and staging environment (env: "staging") using filter aggregations.
🎯 Practice Exercise 1: Create filter aggregations to compare metrics for different regions (US, EU, APAC).
🎯 Practice Exercise 2: Build a query comparing before/after deployment: filter by timestamp before and after deployment time.
🎯 Practice Exercise 3: Use filters aggregation to analyze mobile vs web traffic separately.
💡 Quick Exercise: Add a global aggregation to calculate overall statistics alongside your filtered results.
Lesson 2.6 Advanced Statistics: Extended Stats & Variance
Use case: Get comprehensive statistical analysis including standard deviation, variance, and confidence intervals for performance metrics.
JSON DSL
{
  "size": 0,
  "aggs": {
    "latency_stats": {
      "extended_stats": {
        "field": "latency"
      }
    },
    "response_time_variance": {
      "stats": {
        "field": "response_time"
      }
    }
  }
}
Pro-tip: Extended stats provides: count, min, max, avg, sum, sum_of_squares, variance, std_deviation, std_deviation_bounds. Use for anomaly detection!
Challenge: Calculate extended statistics for latency and identify outliers using standard deviation bounds.

Lesson 2.7 Bucketing Strategies: Range & Histogram Aggregations
Use case: Group data into custom ranges (e.g., latency buckets: 0-100ms, 100-500ms, 500-1000ms, >1000ms) or create automatic histograms.
JSON DSL
{
  "size": 0,
  "aggs": {
    "latency_ranges": {
      "range": {
        "field": "latency",
        "ranges": [
          { "to": 100 },
          { "from": 100, "to": 500 },
          { "from": 500, "to": 1000 },
          { "from": 1000 }
        ]
      }
    },
    "response_histogram": {
      "histogram": {
        "field": "response_size",
        "interval": 1000
      }
    }
  }
}
Pro-tip: Range aggregations are great for SLA analysis. Histogram aggregations automatically create buckets with fixed intervals.
Challenge: Create a query with custom ranges to categorize error severity: low (1-10), medium (11-50), high (51-100), critical (>100).
🎯 Practice Exercise 1: Build SLA compliance query: categorize by latency ranges and count requests in each.

Path 3: Automation & Complex Processing

Lesson 3.1 Nested Objects: Precise Array Filtering
Use case: Find documents where a user has name="admin" AND permission="write" within the same object in the users array.
JSON DSL
{
  "query": {
    "nested": {
      "path": "users",
      "query": {
        "bool": {
          "must": [
            { "term": { "users.name": "admin" } },
            { "term": { "users.permission": "write" } }
          ]
        }
      }
    }
  }
}
Pro-tip: Without nested, Elasticsearch flattens arrays, leading to incorrect matches (e.g., user A with name="admin" and user B with permission="write" would incorrectly match).
Challenge: Write a nested query to find logs where an item in the products array has both category="electronics" AND price > 1000.
🎯 Practice Exercise 1: Find documents with nested arrays where specific conditions are met in the same nested object.
🎯 Practice Exercise 2: Create nested queries with multiple levels of filtering.
💡 Quick Exercise: Try combining nested queries with regular queries to filter documents that have specific nested properties AND top-level properties.
Lesson 3.2 Scripting (Painless): Custom Logic Power
Use case: Filter documents based on complex calculations between fields that don't have built-in operators, or transform data on-the-fly.
JSON DSL
{
  "query": {
    "script": {
      "script": {
        "source": "doc['actual_latency'].value > doc['expected_latency'].value * params.threshold",
        "params": { "threshold": 1.5 }
      }
    }
  }
}
Pro-tip: Painless scripting is powerful but resource-intensive. Always use filters first to reduce document count, then apply scripts.
Challenge: Write a script to find logs where the ratio of error_count to total_requests exceeds 10%.
🎯 Practice Exercise 1: Create a script to calculate custom metrics: (latency - baseline) / baseline to find percentage deviation.
🎯 Practice Exercise 2: Use script to identify anomalies based on multiple field conditions.

Lesson 3.4 Query Optimization: Making Queries Faster
Use case: Optimize slow queries by using better filters, reducing aggregation complexity, and leveraging caching.
Optimization Techniques
// BEFORE: Slow query with match on high-cardinality field
{
  "query": { "match": { "service": "payment" } }
}

// AFTER: Fast query using term on keyword field
{
  "query": { "term": { "service.keyword": "payment" } }
}
Pro-tip: Use GET /_profile API to profile queries and understand where time is spent. Always use filters instead of must for boolean conditions.

Lesson 4.2 Caching Strategies: Speeding Up Repeated Queries
Use case: Leverage Elasticsearch caching mechanisms to speed up frequently executed queries and aggregations.
Caching Best Practices
// Query cache works best with filter context
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "status.keyword": "ERROR" } },
        { "range": { "@timestamp": { "gte": "now-1h" } } }
      ]
    }
  }
}

// Clear cache when needed
POST /_cache/clear
Pro-tip:
  • Filter context queries are cached automatically
  • Request cache works best for aggregations with size: 0
  • Avoid fielddata on high-cardinality text fields (use keyword instead)
Challenge: Monitor cache hit rates using GET /_nodes/stats/indices/query_cache and optimize queries with low hit rates.

Lesson 4.3 Index Design for Performance
Use case: Design optimal index mappings, shard strategies, and rollover policies for large-scale log analysis systems.
Optimized Index Template
{
  "index_patterns": ["logs-*"],
  "template": {
    "settings": {
      "number_of_shards": 3,
      "number_of_replicas": 1,
      "refresh_interval": "30s"
    },
    "mappings": {
      "properties": {
        "@timestamp": { "type": "date" },
        "message": {
          "type": "text",
          "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } }
        },
        "service": { "type": "keyword" }
      }
    }
  }
}
Pro-tip:
  • Size shards between 10-50GB for optimal performance
  • Use ILM (Index Lifecycle Management) for automatic rollover
  • Set appropriate ignore_above for keyword fields to save memory
  • Consider using constant_keyword for fields with same value across all docs
Challenge: Design a complete index template for a high-volume log system with optimal performance characteristics.
🎯 Practice Exercise 1: Create index templates for different use cases (logs, metrics, traces).
🎯 Practice Exercise 2: Implement ILM policies for automatic index management.
