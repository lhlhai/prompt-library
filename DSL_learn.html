Lộ trình 1: Tìm kiếm Log thần tốc

Lesson 1.1 Term vs Match: Khi nào dùng cái nào?
Use case: Bạn có ID giao dịch TX12345. Dùng term để tìm chính xác. Bạn có câu log "User login failed". Dùng match để tìm theo từ khóa.
JSON DSL
{
  "query": {
    "bool": {
      "must": [
        { "term": { "transaction_id.keyword": "TX12345" } },
        { "match": { "message": "failed" } }
      ]
    }
  }
}
Pro-tip: Luôn dùng .keyword cho các trường text nếu muốn tìm chính xác (case-sensitive). Trường text thông thường sẽ được phân tách thành các từ đơn lẻ.
Challenge: Viết query tìm log có request_id là "REQ-999" và trong message có chứa từ "timeout".
Lesson 1.2 Wildcard & Fuzzy: Tìm khi không nhớ rõ
Use case: Tìm log của các service bắt đầu bằng auth-* hoặc tìm từ khóa bị gõ sai (vd: conection thay vì connection).
JSON DSL
{
  "query": {
    "bool": {
      "should": [
        { "wildcard": { "service.keyword": "auth-*" } },
        { "fuzzy": { "message": { "value": "conection", "fuzziness": 1 } } }
      ]
    }
  }
}
Challenge: Tìm tất cả các log từ các service có tên chứa từ "payment" (dùng wildcard) và có thông báo lỗi gần giống với "database".
Lesson 1.3 Range & Time: Lọc theo thời gian
Use case: Tìm log trong 24h qua hoặc tìm các request có thời gian phản hồi (latency) cực cao.
JSON DSL
{
  "query": {
    "range": {
      "@timestamp": {
        "gte": "now-24h",
        "lte": "now"
      }
    }
  }
}
Pro-tip: Sử dụng các toán tử gte (>=), gt (>), lte (<=), lt (<). Đối với thời gian, now-1d, now-1h là những phím tắt cực kỳ hữu dụng.
Challenge: Tìm các log có response_time lớn hơn 5000ms trong khoảng thời gian từ 2 ngày trước đến 1 ngày trước.
Lesson 1.4 Logic Bool: Kết hợp điều kiện
Use case: Kết hợp nhiều điều kiện: Phải là lỗi, Phải trong 1h qua, và KHÔNG được từ service test-bot.
JSON DSL
{
  "query": {
    "bool": {
      "must": [ { "match": { "level": "ERROR" } } ],
      "filter": [ { "range": { "@timestamp": { "gte": "now-1h" } } } ],
      "must_not": [ { "term": { "service.keyword": "test-bot" } } ]
    }
  }
}
Pro-tip: Luôn ưu tiên dùng filter thay vì must cho các điều kiện đúng/sai tuyệt đối (như thời gian, status code) vì filter nhanh hơn và được cache.

Lộ trình 2: Phân tích dữ liệu Log

Lesson 2.1 Aggregations cơ bản: Thống kê nhanh
Use case: Tính trung bình thời gian phản hồi hoặc tìm request chậm nhất trong hệ thống.
JSON DSL
{
  "size": 0,
  "aggs": {
    "avg_latency": { "avg": { "field": "latency" } },
    "max_latency": { "max": { "field": "latency" } }
  }
}
Challenge: Viết query tính tổng (sum) dung lượng bytes_sent của tất cả các request có status 200.
Lesson 2.2 Grouping: Nhóm theo Service & Thời gian
Use case: Đếm số lượng lỗi theo từng service hoặc vẽ biểu đồ lỗi theo từng phút.
JSON DSL
{
  "size": 0,
  "aggs": {
    "errors_over_time": {
      "date_histogram": {
        "field": "@timestamp",
        "fixed_interval": "1h"
      }
    }
  }
}
Pro-tip: Kết hợp terms aggregation bên trong date_histogram để xem top các lỗi trong mỗi khoảng thời gian.
Lesson 2.3 Thống kê nâng cao: Percentiles
Use case: Bạn muốn biết 95% người dùng có thời gian phản hồi dưới bao nhiêu ms (P95). Đây là chỉ số quan trọng hơn giá trị trung bình!
JSON DSL
{
  "size": 0,
  "aggs": {
    "latency_stats": {
      "percentiles": {
        "field": "latency",
        "percents": [50, 95, 99]
      }
    }
  }
}
Challenge: Tính số lượng customer_id duy nhất (dùng cardinality) đã gặp lỗi trong 24h qua.

Lộ trình 3: Tự động hóa & Xử lý phức tạp

Lesson 3.1 Nested Objects: Lọc chính xác trong mảng
Use case: Tìm document có user có name="admin" VÀ permission="write" trong cùng một object thuộc mảng users.
JSON DSL
{
  "query": {
    "nested": {
      "path": "users",
      "query": {
        "bool": {
          "must": [
            { "term": { "users.name": "admin" } },
            { "term": { "users.permission": "write" } }
          ]
        }
      }
    }
  }
}
Pro-tip: Nếu không dùng nested, Elasticsearch sẽ làm phẳng (flatten) mảng, dẫn đến việc tìm kiếm sai lệch (ví dụ: user A có name="admin" và user B có permission="write" cũng sẽ bị khớp).
Lesson 3.2 Scripting: Sức mạnh tùy biến
Use case: Lọc các document dựa trên một phép tính logic phức tạp giữa hai trường mà không có sẵn toán tử.
JSON DSL
{
  "query": {
    "script": {
      "script": {
        "source": "doc['actual_latency'].value > doc['expected_latency'].value * params.threshold",
        "params": { "threshold": 1.5 }
      }
    }
  }
}
Pro-tip: Scripting (Painless) rất mạnh nhưng tốn tài nguyên. Hãy luôn cố gắng dùng các query chuẩn trước khi tìm đến script.
Lesson 3.3 Performance: Profile & Explain
Use case: Query của bạn chạy quá chậm? Hãy dùng profile: true để xem Elasticsearch đã tốn bao nhiêu thời gian cho từng bước.
JSON DSL
{
  "profile": true,
  "query": {
    "match": { "message": "critical error" }
  }
}
Thử thách cuối cùng: Hãy viết một query tìm tất cả log của service payment trong 24h qua, có chứa lỗi "timeout", nhóm kết quả theo từng giờ, và trong mỗi giờ hãy đếm số lượng customer_id duy nhất gặp lỗi này.
